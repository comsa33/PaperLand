# 리스크 및 미해결 질문

## 핵심 리스크

### R1. "그럴듯해 보이지만 쓸모없는 지도" 함정
- 임베딩+UMAP은 늘 예쁜 그림을 만듦 → 사용자가 실제 인사이트를 얻는지는 별개
- **대응**: Phase 1 직후 본인+동료 5명에게 "이 지도로 뭐 알게 됐어?" 인터뷰

### R2. 빈 땅의 의미 해석 어려움
- 임베딩 공간의 빈 영역 ≠ 의미 있는 공백 후보
- 좌표축이 의미 불명확 → 사용자가 "왜 저밀도인지" 이해 못 함
- **대응**:
  - **MVP**: 인접 논문·키워드 기반 템플릿 설명 (LLM 미사용)
  - **V1+**: LLM 자연어 설명 (사용자 동의 시)

### R3. UMAP 좌표 불안정성
- 신규 논문 추가 시 좌표가 흔들리면 사용자 멘탈모델 깨짐
- **대응**: Procrustes 정렬 + 신규 논문은 transform()만, 재학습은 분기 단위

### R4. 임베딩 모델의 분야 편향
- 일반 도메인 임베딩은 특정 분야(생물·물리)에서 표현력 약함
- **대응**: 분야별 임베딩 모델 선택지 제공 또는 도메인 특화 시작 (cs만 먼저)

### R5. 데이터 양과 렌더링 성능
- 50만+ 논문 점 단위 렌더는 무거움
- **대응**: hex bin 집계 우선, 줌인 시에만 개별 논문 로드 (LOD)

### R6. 차별화 약화
- Connected Papers, Litmaps 등이 유사 기능 추가하면?
- **대응**: "빈 땅" 강조 + 게임적 메타포로 정체성 유지

### R7. 학술 데이터 라이선스
- arXiv는 메타데이터 자유롭지만, 인용 데이터(Semantic Scholar)는 약관 확인 필요
- **대응**: 출처 명시, 비상업 시작 → 상업화 전 재검토

### R8. 비공개 abstract 입력 시 정보 유출 (CRITICAL)
- 시나리오 2("내 abstract 지도에 올려보기")는 unpublished 아이디어를 다룸 → 민감
- 위험: 외부 LLM API 전송, 서버 저장, 임베딩 캐시 노출 등
- **대응 원칙**:
  1. **기본은 클라이언트 처리 또는 자체 호스팅 임베딩 모델** (sentence-transformers 로컬)
  2. **저장 안 함** (메모리만 사용, 세션 종료 시 폐기)
  3. **외부 LLM 전송은 명시적 사용자 동의 후에만** (체크박스 + 무엇이 전송되는지 고지)
  4. **로그·텔레메트리에 abstract 본문 미포함**
  5. UI에 "이 입력은 서버에 저장되지 않습니다" 명시
- 이 원칙이 안 지켜지면 시나리오 2 자체를 V1 이후로 미룸

## 미해결 질문 (사용자 결정 필요)

### Q1. 도메인 범위
- arXiv 전체? cs만? 특정 서브분야부터?
- → **추천**: cs.CL 또는 cs.LG 한 분야로 시작 (사용자 본인 친숙도 ↑)

### Q2. 시각화 스타일 톤
- 게임/땅따먹기 메타포 강하게 (귀엽고 직관적)
- vs. 학술 지도 톤 (전문적·신뢰감)
- → **추천**: 베이스는 학술 톤, 빈 땅·점유 표현만 게임적 요소 가미

### Q3. 공개 vs 사이드 프로젝트
- 공개 서비스로 운영? 본인 연구용 도구?
- → 운영 부담 큼. 초기엔 본인 사용 + 데모 정도 권장

### Q4. 개발 인력 (RESOLVED)
- 혼자 풀스택 1인으로 가정.
- **V0 스택 확정**: Next.js + deck.gl 정적 웹앱 + 노트북 기반 오프라인 파이프라인 (08-v0-scope 참조).
- (이전 "노트북+streamlit" 추천은 폐기 — V0 스코프가 충분히 작아 곧바로 Next.js로 시작 가능 판단)

### Q5. LLM 통합 범위
- 빈 영역 설명·연구 가설 생성에 LLM 사용?
- → 좋은 차별점이지만 비용·신뢰성 이슈 → V1 이후 검토 권장

### Q6. 평가 지표
- "성공"의 정의는?
  - 베타 유저 N명?
  - "이 지도로 연구 주제 정했다" 사례 1건?
  - GitHub star?
- → **추천**: 본인이 직접 새 연구 주제 하나를 이 도구로 발굴해보기 = 진정한 dogfooding
